# PvP 확률 계산기

`/planner/pvp/` (`Planner:pvp`)는 제공된 PvP 개편 공식으로 **입력한 스탯의 기본 확률**을
계산한다. 사이드바의 Planner 바로 다음, Buy me a coffee 앞에서 접근한다.
기존 Planner 경로와 기능은 유지하며 새 페이지는 static sitemap에도 등록한다.
Django는 GET 렌더링만 제공하고 POST는 405로 거부한다. 입력의 서버 저장이나 DB 쓰기는 없다.
클라이언트 계산은 importer, DB 게임 데이터, PvE 및 대미지 계산에 의존하지 않는다.
별도 카드·버프·특성의 확률 보너스를 자동 합산하지 않는다.
이 문서는 사용자가 제공한 공식의 구현을 설명하며 실제 게임 패치 완료를 주장하지 않는다.

## 입력과 결과의 방향

| 입력 | 의미 |
| --- | --- |
| 내 레벨 / 상대 레벨 | 명중에만 적용하는 레벨 보정의 기준 |
| 내 명중 / 상대 회피 | 내 공격의 명중률과 상대 회피율 |
| 내 치명타 발생 / 상대 치명타 저항 | 내 치명타 확률 |
| 내 블록 / 상대 블록 관통 | **내 방어 블록 확률** |

네 확률과 레벨 보정 계수가 입력 즉시 갱신된다. 상대 회피는 레벨 보정이 끝난 내 최종 명중의
여확률이다. 블록 결과는 상대의 블록 확률이 아니다. 확률은 소수 둘째 자리의 %로,
보정 계수는 소수 둘째 자리와 ×로 표시한다. 계산 내부는 반올림 전 값을 사용한다.
아주 작은 양의 확률은 화면에서 0.00%로 반올림될 수 있다.

초기값은 양쪽 레벨 500, 모든 스탯 20,000이다. 명중 90%, 상대 회피 10%, 치명타 10%,
내 블록 30%, 계수 1을 바로 표시한다. 초기화 버튼은 여덟 입력을 모두 이 기본값으로
되돌리고 오류 표시도 제거한다. 영 스탯도 허용하며 같은 스탯과 레벨이면 같은 기준값을 낸다.

## 제공 공식

```text
명중률(%) = 100 / (1 + (1/9) × ((상대 회피 + 10) / (내 명중 + 10))²) × 레벨 보정
상대 회피율(%) = 100 − 최종 명중률(%)
치명타 확률(%) = 100 / (1 + 9 × ((상대 치명타 저항 + 10) / (내 치명타 발생 + 10))²)
내 블록 확률(%) = 100 / (1 + (7/3) × ((상대 블록 관통 + 10) / (내 블록 + 10))²)
레벨 보정 = max(0, 1 − max(0, 상대 레벨 − 내 레벨) / 50)
```

상대가 높을 때만 명중이 줄어든다. 내 레벨이 더 높아도 보너스를 주지 않으며 치명타와
블록에는 레벨 보정을 곱하지 않는다. 같은 스탯에서 상대가 25레벨 높으면 명중 45%,
상대 회피 55%이며 49레벨 높으면 명중 1.8%, 상대 회피 98.2%다.
**상대가 50레벨 이상 높으면 명중은 0%, 상대 회피는 100%**다.
따라서 레벨 보정 전 확률이 스탯 비율에 따라 부드럽게 변한다는 설명을 모든 상황에서
명중이 양수라는 뜻으로 해석하면 안 된다.

치명타 발생 25,000 대 저항 20,000은 약 14.8%(화면 14.79%)다.
각 스탯의 +10 때문에 원래 스탯의 배율이 같아도 작은 스탯에서는 결과가 다르다.
내 명중 10 대 회피 0은 약 97.30%, 내 치명타 발생 10 대 저항 0은 약 30.77%,
내 블록 10 대 상대 관통 0은 약 63.16%다. 상대 관통이 커질수록 내 블록은 감소한다.

## 언어·접근성과 표시

`settings.REGION`이 `ktos` 또는 `ktest`이면 새 페이지의 제목·입력 label·결과·기본값 설명·
버튼·안내·오류를 한국어로 제공한다. 그 외 지역은 영어다. 기존 전역 번역 동작을 바꾸지 않으며
사이드바 메뉴는 기존 스타일의 `PvP Calculator`를 사용한다.

어두운 공통 테마와 반응형 사이드바를 재사용한다. 계산기 CSS는 해당 페이지에만 적용한다.
390px 화면에서는 입력과 결과를 한 열로 배치한다. 각 입력에 연결된 label과 오류 설명이 있고,
키보드 Tab으로 여덟 입력과 초기화 버튼에 접근한다. 결과 영역은 `aria-live="polite"`,
`aria-atomic="true"`로 갱신하며 오류 필드는 `aria-invalid`로 표시한다.
JavaScript가 꺼져 있으면 활성화 안내를 표시하고 결과는 `—`로 남긴다.
새 외부 패키지·이미지·차트는 추가하지 않는다.

## 입력 안전 범위와 오류

| 대상 | 허용 범위 |
| --- | --- |
| 양쪽 레벨 | 0~10,000의 정수 |
| 여섯 스탯 | 0~1,000,000,000,000; 소수 허용 |
| 입력 문자열 | 앞뒤 공백 제거 후 최대 64자; 십진수 또는 지수 표기 |

`20000`, `20000.5`, `.5`, `2e4`, `+2e4` 같은 표기를 허용한다.
레벨의 `500.0`, `5e2`도 변환 결과가 정수이므로 허용한다.
빈 값, 음수 부호(문자열 `-0` 포함), 비숫자, `NaN`, 무한대, 16진수, 쉼표,
범위 초과와 너무 긴 입력은 거부한다. JS가 표현할 수 없어 0으로 언더플로하는
0이 아닌 입력도 거부한다. 특히 `-1e-400`은 `Number()`가 `-0`으로 만들기 전에
부호 검사로 거부한다. `1e-400` 역시 표현 불가 값으로 거부한다.

하나라도 잘못되면 필드별 오류와 공통 안내를 표시하고 **모든 확률과 보정 계수를 `—`로
교체**한다. 입력한 문자열을 몰래 보정하거나 마지막 유효 결과를 유지하지 않는다.
모든 입력을 고치면 결과와 오류 상태가 즉시 복구된다. 서버 쿼리 인자로 기본 입력을 덮어쓰지 않는다.

계산은 JavaScript 부동소수점 숫자를 사용한다. +10으로 분모의 영을 피하고 위 범위로
비율과 제곱을 유한하게 제한하여 유효한 큰 입력에서도 확률을 0~100%로 계산한다.
임의 정밀도 연산이나 게임의 정수 처리·내부 반올림을 재현하는 도구는 아니다.

## 검증 경로와 증거의 한계

`harness/test_pvp_calculator.py`는 기본 pytest 수집 이름을 사용하며 실제 제공 파일
`TavernofSoul/static/js/pvp-calculator.js`를 Node에서 실행한다. Node 부재나 실행 실패를
skip으로 바꾸지 않는다. 계산식을 테스트에 다시 구현하지 않고 고정 기준값·독립 예시와
여확률·단조성·방향성으로 검사한다. 동일/영 스탯, +10 효과, 25,000 대 20,000,
레벨 49/50/51 경계와 높은 내 레벨의 무보너스, 치명타·블록의 레벨 독립성,
큰 유효값, 범위·문법·음수 언더플로 오류를 다룬다.
테스트 내부 DOM 대역은 제공 스크립트의 즉시/DOMContentLoaded 시작,
input/change/submit/reset 연결, 오류 시 전체 결과 제거와 초기화를 검사한다.
이 대역만으로 실제 HTML·CSS·브라우저 접근성을 입증하지는 않는다.

`harness/tests.py`의 기존 `PipelineTests`에 URL 역참조·실제 렌더링·입력 label·지역 문구·
메뉴 순서·sitemap 등록·GET/POST의 DB 쓰기 부재 검증을 추가한다.
기존 테스트 선택 범위와 importer 회귀 검증을 유지한다.

`harness/browser/equipment.spec.js`와 `manifest.json`은 기존 9개 시나리오를 보존하고
다음 정확한 제목의 실제 브라우저 시나리오 2개를 추가한다.

- `pvp calculator updates probabilities and level boundaries`
- `pvp calculator rejects invalid inputs and resets accessibly`

각각 desktop/mobile에서 실행하며 모바일 폭은 390px이다. 실제 사이드바 링크·입력·결과·
레벨 경계·음수 언더플로 등의 오류·초기화·키보드 이동·가로 넘침을 검사하고 기존
`evidence(page, info, name)`로 확률·오류·초기화 screenshot을 남긴다.
`harness/test_browser_runner.py`는 등록된 11개 시나리오와 두 viewport의 정확한
22개 조합을 요구한다. 조합별 누락 또는 중복 대체를 거절하며 기존 실패·skip·재시도·
불완전 보고서 거절도 유지한다. 합계만 22인 보고서를 완전성 근거로 삼지 않는다.

이 작성 단계에서는 검사를 실행하지 않았다. 테스트 명세와 문서는 성공 증거가 아니다.
이전 run의 실패·중단 기록 및 부분 검사 성공은 새 최종 결과의 증거로 재사용하지 않는다.
상위 오케스트레이터가 표준 새 `make agent-workflow`에서 등록된 실제 구현 모델 뒤에
**새 Claude 전체 의미 검토 → full `make check` → scoped apply → Git 역할**을 수행한다.
검토는 매번 `documentation={status,files,reason}`을 반환하고 문서 완전성은 의미로 판단한다.
문서 확장자 검사만으로 완료 판정하지 않는다. 검토에는 공식 방향·입력 범위·오류와
복구·언어·격리 경계가 최종 제품 소스 및 테스트와 맞는지 포함한다.

하네스 변경이 있으므로 full `make check`가 필수다. 별도 Chromium container 검증과
최종 GitHub required CI 3개의 실제 success 확인, 기존 bridge의 CI/merge/cleanup은
상위 담당이다. 기본 `GIT=1`, 기존 역할·모델·인증·예산·검증 강도를 유지하며 별도 복원 런처,
copy hook, runner override 또는 자동 재개를 도입하지 않는다. 하네스·배포·게시 정책이나
주요 아키텍처 결정 변경이 없으므로 새 ADR은 필요하지 않다. 운영 배포는 이 개발 범위 밖이다.
합성 입력과 선택된 viewport의 검증은 실제 게임 패치 적용, 모든 장치의 접근성 또는
실제 서버 전투 확률의 관측을 대신하지 않는다.
